# 26. Agregar el campo refreshTokenHash al modelo de usuario

Igual que con el password, no vamos a guardar el refresh token en texto plano en la base de datos — guardamos un hash. Además, este campo es lo que nos va a permitir revocar una sesión más adelante (en feature/auth-logout): un JWT por sí solo es imposible de invalidar antes de su expiración natural, porque el servidor no "recuerda" haberlo emitido. Este campo es justamente la memoria que le estamos dando al servidor.

# 27. Generar un secret y refresh expires, y agregar en .env

node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"

JWT_REFRESH_SECRET=<el valor generado>
JWT_REFRESH_EXPIRES_IN=7d

¿Por qué un secreto distinto al del access token? Si en algún momento se filtra uno de los dos secretos, el daño queda contenido — con JWT_SECRET comprometido alguien podría forjar access tokens, pero no refresh tokens (y viceversa). Son dos "llaves" independientes aunque ambas vivan en el mismo .env.

# 39. Porque el registro nunca deja elegir el rol?

En register (de hace varias features) nunca leímos req.body.role — el modelo simplemente pone 'user' por defecto. Esto es intencional: si el endpoint aceptara role desde el cliente, cualquiera podría registrarse mandando { "role": "admin" } y auto-otorgarse permisos. El rol de un usuario solo debería poder cambiarlo alguien que ya es admin, nunca el propio usuario al crearse. No hace falta tocar código en este paso — es simplemente confirmar que esa puerta ya estaba bien cerrada desde el principio.
